# Optimization research workflow

The active tasks are listed in `tasks.json`: 001, 002, and 003. Other tasks are deferred. Use this workflow when developing a candidate; changes to the benchmark itself require a separate, explicitly scoped task.

Keep held-out inputs, saved reference answers, validation logs, final freeze records and final run outputs outside the repository/development workspace. The maintainer's default private root is `~/SocialSciBench-private/`; it must not be exposed to a development agent. Path separation alone does not restrict access by processes under the same user account.

1. Read the task's `task.md`, `task.json`, `reference.py`, and `workloads.py`, then `DATA.md` when present and `harness/README.md`. Preserve the estimator, numerical conventions, output identities, and full timing boundary.
2. Start from a candidate under `solutions/<task>/<candidate>/` with `python -m harness init-solution`. Only edit that candidate's declared sources and research/build artifacts. Keep `research.md`, `requirements.lock`, and `build.md` current; declare additional artifacts in `solution.json`. Do not edit task definitions, references, generators, the evaluator, or recorded baselines to improve a candidate's score.
3. Research relevant algorithms, papers, library documentation and implementations when network tools are available. Record source URLs, versions, hypotheses, expected bottlenecks, and unsuccessful attempts in the candidate's `research.md`. In an independent evaluation, do not retrieve prior SocialSciBench candidates or results; general algorithm/library research is allowed. In an informed research session, prior results may be consulted when authorized by the experiment policy.
4. Run `evaluate --smoke` first. Then evaluate workload 1 and representative larger workloads, including difficult structures. Iterate on measured bottlenecks. Develop only on synthetic and `real-development` workloads. Task 001/109 (`real-smoke`) is for compatibility/crash checks only, never speed or accuracy tuning. Do not inspect or execute held-out workloads/results during development. Freeze code and settings with `harness freeze` before final evaluation with `harness final`; report every round, including failures, and keep the whole study to two or three rounds across versions. Run every workload in the claimed scope before claiming task-wide correctness or performance. Additional `--validation-seed` values provide robustness checks; public fixtures are not a hidden test set.
5. Follow the user's compute/time budget. If none is provided, begin with one thread, the default 300-second worker timeout, and at most 30 minutes of experiments before reporting progress. Record any incomplete workloads; timeout or a passed smoke check is not a full-task success. Set target hardware and install candidate dependencies explicitly before running. Do not run benchmarks concurrently on the same host.
6. Return a `solution.json` with all source files, artifact paths and dependency declarations, research notes, the run-directory paths, and a report of passing/failing cases. Report absolute timings alongside speedups and their measurement scope. A new invocation writes a new run; never overwrite or cherry-pick historical measurements. Use `harness export` for portable run bundles and `harness replay` to repeat saved cases/settings in a new run after installing the recorded environment.

Candidate rules: accept the documented keyword arguments; return host-ready NumPy arrays and Python scalars; do not mutate inputs. Do not read expected outputs, import the benchmark's reference at runtime, infer answers from workload seeds, cache outputs across invocations, change timers/validators, or inspect the evaluator's execution state. Data-independent compilation and reusable code caches are allowed; input-dependent preprocessing belongs inside each `run` call. Native libraries are allowed through a Python adapter. Accelerator submissions must provide a synchronization hook, with transfers and output conversion inside the timed adapter.

For independent-agent evaluation, use `python -m harness stage --task ID --out NEW_DIRECTORY` (add `--suite real-development --ids ...` to include selected development inputs) and give the agent access only to that exported workspace. This tool selects files; it does not impose operating-system access restrictions. Use an external container or runner to enforce filesystem and network visibility when required. The local evaluator executes trusted candidate code in separate processes; it is not a security sandbox for hostile submissions.
